# Выбор и настройка мониторинга в системе

## Мотивация

### Почему системе нужен мониторинг?

На данный момент компания «Александрит» располагает только Яндекс Метрикой, которая отслеживает поведение пользователей
на сайте. Однако после открытия API для партнёров и роста числа заказов (как B2C, так и B2B) данных Метрики стало
недостаточно.

**Что мы теряем без мониторинга:**

1. **Слепоту в отношении API и интеграций** - мы не видим, сколько запросов приходит от партнёров, с какой задержкой
   отвечает MES, сколько заказов теряется в очередях.
2. **Невозможность обнаружить проблемы до клиентов** - жалобы от B2C и партнёров поступают уже постфактум, когда
   репутация испорчена, а контракты расторгнуты.
3. **Отсутствие данных для оптимизации** - мы не знаем, почему дашборд MES тормозит, и не можем принять обоснованное
   решение.
4. **Невозможность планировать масштабирование** - без метрик RPS, времени ответа и использования ресурсов мы не знаем,
   когда и какие компоненты нужно расширять.
5. **Ручное реагирование на инциденты** - каждый сбой или замедление требует, чтобы кто-то из клиентов или операторов
   сообщил об этом.

### Что даст мониторинг

| Для бизнеса                            | Выгода                                                                          |
|----------------------------------------|---------------------------------------------------------------------------------|
| Сокращение времени реакции на проблемы | Обнаружение инцидента за короткое время вместо часов/дней                       |
| Удержание клиентов и партнёров         | Возможность гарантировать SLA (например, расчёт цены за 3 минуты)               |
| Снижение операционных затрат           | Операторы не тратят время на ручное отслеживание «зависших» заказов             |
| Обоснованное планирование мощностей    | Точные данные для закупки дополнительных инстансов или увеличения квот в облаке |
| Повышение доверия к команде разработки | Прозрачность: бизнес видит, какие метрики улучшаются после релизов              |

## Выбор подхода к мониторингу

### Используемые подходы

Мы будем комбинировать **RED** и **USE** подходы, а также добавим специфические метрики RabbitMQ и БД.

| Подход                                    | Для каких компонентов                           | Почему                                                                                                             |
|-------------------------------------------|-------------------------------------------------|--------------------------------------------------------------------------------------------------------------------|
| **RED** (Rate, Errors, Duration)          | Онлайн-магазин, CRM, MES API, API для партнёров | Ориентирован на пользовательский опыт и SLA. Позволяет ответить: сколько запросов, сколько ошибок, какая задержка. |
| **USE** (Utilization, Saturation, Errors) | Инфраструктура: CPU, память, диски, сеть, БД    | Классический подход для выявления узких мест и насыщения ресурсов.                                                 |
| **Специфические метрики**                 | RabbitMQ (очереди, dead-letter), S3, размеры БД | Критичны для сценариев асинхронной обработки и хранения 3D-моделей.                                                |

## Отслеживаемые метрики

### 1. Метрики уровня приложений (API)

| Метрика                                               | Зачем                                                                  | Ярлыки                                                    |
|-------------------------------------------------------|------------------------------------------------------------------------|-----------------------------------------------------------|
| **Number of requests (RPS) для shop / CRM / MES API** | Понимать нагрузку, тренды, планировать масштабирование                 | `service` (shop/crm/mes), `method` (GET/POST), `endpoint` |
| **Response time (latency) для API**                   | Измерять соответствие ожиданиям клиентов. Для расчёта цены - критично. | `service`, `endpoint`, `quantile`                         |
| **Number of HTTP 200 / 500 для API**                  | Отслеживать долю успешных и ошибочных запросов                         | `service`, `endpoint`                                     |
| **Number of requests (RPS) per user**                 | Выявлять аномальную активность (боты, DDoS, ошибки в интеграции)       | `service`, `user_id` (хешированный)                       |
| **Number of simultaneous sessions**                   | Оценивать количество активных пользователей / партнёров                | `service`                                                 |

### 2. Метрики RabbitMQ (очереди)

| Метрика                                    | Зачем                                                                                | Ярлыки                 |
|--------------------------------------------|--------------------------------------------------------------------------------------|------------------------|
| **Number of messages in flight**           | Понимать, сколько заказов ожидают обработки (расчёт цены, создание в CRM)            | `queue_name`           |
| **Number of dead-letter-exchange letters** | Обнаруживать заказы, которые не удалось обработать (ошибки в MES, невалидные модели) | `queue_name`, `reason` |

### 3. Инфраструктурные метрики (USE)

| Метрика                             | Зачем                                                           | Ярлыки                      |
|-------------------------------------|-----------------------------------------------------------------|-----------------------------|
| **CPU % для shop / CRM / MES API**  | Выявлять нехватку CPU (особенно для расчёта 3D-полигонов в MES) | `instance_id`               |
| **Memory Utilisation для API и БД** | Избегать OOM и свопинга                                         | `instance_id`/`db_instance` |
| **Number of connections для БД**    | Предотвращать исчерпание пула соединений                        | `db_name`                   |

### 4. Хранилища (S3 и БД)

| Метрика                            | Зачем                                                                | Ярлыки    |
|------------------------------------|----------------------------------------------------------------------|-----------|
| **Size of S3 storage**             | Отслеживать рост загружаемых 3D-моделей (влияет на стоимость облака) | `bucket`  |
| **Size of shop / MES db instance** | Планировать расширение дисков                                        | `db_name` |

## План действий

### Этап 1. Базовая инфраструктура мониторинга (1-2 недели)

1. **Поднять time-series базу данных**
    - Выбор: **Prometheus**
    - Размещение: в облаке (Yandex Managed Service for Prometheus или самостоятельный EC2 + EBS).

2. **Установить экспортёры**
    - Node Exporter (на каждый EC2-инстанс) - для CPU, память, диск, сеть.
    - cAdvisor или контейнерный экспортёр (если перейдём на ECS/K8s).
    - RabbitMQ Prometheus Exporter - для очередей.
    - Database exporter (для PostgreSQL/Yandex Managed DB) - для соединений, размера, репликации.

3. **Внедрить клиентские библиотеки для приложений**
    - Для Java (Spring Boot): **Micrometer** - экспорт метрик в Prometheus.
    - Для C# (MES): **Prometheus.Client** или **OpenTelemetry**.
    - Метрики: RPS, latency, HTTP status, количество активных сессий.

4. **Настроить визуализацию**
    - **Grafana** (облачный или self-hosted).
    - Создать дашборды:
        - «RED для API» (RPS, ошибки, latency p95).
        - «USE для инстансов» (CPU, память, диск).
        - «RabbitMQ health» (длина очередей, dead-letter).
        - «Бизнес-метрики» (количество заказов в статусах, заказов в очереди на расчёт).

5. **Настроить алерты**
    - Использовать **Alertmanager**.
    - Каналы уведомлений: **Slack** (в канал #incidents), **email** для тимлида и продакт-менеджера.

## Дополнительное задание: показатели насыщенности

### Определение пороговых значений насыщенности

| Компонент                 | Метрика насыщения                                  | Пороговое значение                 | Что происходит при превышении                                                                                                                                                                             |
|---------------------------|----------------------------------------------------|------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **MES API (расчёт цены)** | Длина очереди RabbitMQ `price_calculation`         | > 100 сообщений в течение 10 минут | 1. Автоматически создать тикет в Jira «Масштабировать MES-воркеры»<br>2. Отправить алерт в Slack DevOps-инженеру<br>3. Временно увеличить число consumer'ов (если реализовано автоскейлинг)               |
| **Любой API**             | p95 latency > 5 секунд (для не-расчётных запросов) | Превышение за 5 минут              | 1. Алерт «Задержка API»<br>2. Проверить CPU/память инстанса<br>3. Если повторяется - план по добавлению второго инстанса и балансировщика                                                                 |
| **БД (общая)**            | Количество соединений > 80% от `max_connections`   | Достижение порога                  | 1. Алерт «Исчерпание соединений БД»<br>2. Временно увеличить `max_connections` через консоль (если позволяет облако)<br>3. Долгосрочно: внедрить пул соединений с ограничением на приложениях             |
| **CPU MES**               | CPU utilisation > 85% в течение 10 мин             | Высокая утилизация                 | 1. Алерт «MES перегружен»<br>2. Проверить, не запущено ли несколько тяжёлых расчётов одновременно<br>3. Если повторяется - добавить горизонтальные воркеры                                                |
| **Диск БД**               | Использование диска > 85%                          | Критический порог                  | 1. Алерт «Заканчивается место на БД»<br>2. Автоматическое создание задачи на увеличение диска в Yandex Cloud (через API)<br>3. Если автоувеличение невозможно - уведомление DevOps для ручного расширения |
