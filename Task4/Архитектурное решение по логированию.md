# Архитектурное решение по логированию

## 1. Анализ: какие логи собирать и откуда

### Из каких систем требуется сбор логов

| Система                       | Что логируем                                                                     | Почему                                                  |
|-------------------------------|----------------------------------------------------------------------------------|---------------------------------------------------------|
| **Internet Shop**             | Действия пользователя: загрузка файла, нажатие «Сделать заказ», ошибки валидации | Видим проблемы на стороне клиента до отправки на бэкенд |
| **Shop API**                  | Входящие запросы, создание заказа, сохранение в БД, вызовы к S3                  | Основная бизнес-логика заказа                           |
| **CRM API**                   | Получение сообщений из очереди, подтверждение заказа, синхронизация статусов     | Отслеживаем жизненный цикл заказа                       |
| **MES API**                   | Расчёт цены, назначение оператора, изменение статусов производства               | Критический путь заказа                                 |
| **Messages Queue (RabbitMQ)** | Публикация/потребление сообщений, ошибки доставки, dead-letter                   | Обнаружение потерянных сообщений                        |
| **3d files storage (S3)**     | Загрузка/выгрузка файлов, ошибки доступа, время операций                         | Диагностика проблем с 3D-моделями                       |

### Список INFO-логов по системам

**Internet Shop:**

- `USER_UPLOADED_FILE` - user_id, file_name, file_size, timestamp
- `USER_CLICKED_SUBMIT` - user_id, order_id, cart_items
- `FRONTEND_ERROR` - user_id, error_message, browser_info

**Shop API:**

- `ORDER_INITIATED` - order_id, user_id, timestamp
- `ORDER_SUBMITTED` - order_id, user_id, total_amount
- `FILE_UPLOADED_TO_S3` - order_id, s3_key, file_size
- `ORDER_PRICE_REQUEST_SENT` - order_id, queue_name, message_id

**CRM API:**

- `PRICE_CALCULATED_RECEIVED` - order_id, price, calculation_time
- `ORDER_MANUFACTURING_APPROVED` - order_id, seller_id
- `ORDER_CLOSED` - order_id, final_status, closed_by

**MES API:**

- `PRICE_CALCULATION_STARTED` - order_id, polygons_count
- `PRICE_CALCULATION_COMPLETED` - order_id, price, duration_ms
- `ORDER_ASSIGNED_TO_OPERATOR` - order_id, operator_id
- `MANUFACTURING_STARTED` - order_id, operator_id
- `MANUFACTURING_COMPLETED` - order_id, operator_id
- `PACKAGING_STARTED` - order_id
- `SHIPPED` - order_id, tracking_number

**RabbitMQ (через плагин или consumer-лог):**

- `MESSAGE_PUBLISHED` - queue_name, message_id, order_id
- `MESSAGE_CONSUMED` - queue_name, message_id, order_id, consumer_service
- `MESSAGE_DEAD_LETTERED` - queue_name, message_id, reason

**S3 Storage:**

- `FILE_UPLOAD_SUCCESS` - s3_key, size, duration_ms
- `FILE_UPLOAD_FAILED` - s3_key, error_code, error_message
- `FILE_DOWNLOAD_SUCCESS` - s3_key, duration_ms
- `FILE_DOWNLOAD_FAILED` - s3_key, error_code

## 2. Мотивация

В текущей ситуации компания «Александрит» разбирает инциденты исключительно со слов клиентов. Разработчики и поддержка
тратят часы на ручной поиск по логам каждого сервиса в отдельности (через `kubectl logs` или SSH на EC2). Это приводит
к:

1. **Высокому MTTR** (Mean Time To Resolution) - дни вместо часов.
2. **Перегрузке поддержки** - сотрудники вручную копаются в логах трёх разных сервисов.
3. **Потере контекста** - логи разбросаны, нет единой картины по заказу.
4. **Невозможности обнаружить аномалии** - никто не следит за внезапным ростом ошибок.

### Приоритеты внедрения

| Очередь | Система                | Почему в первую очередь                                                           |
|---------|------------------------|-----------------------------------------------------------------------------------|
| **1**   | **MES API**            | Здесь происходят долгие расчёты (2–30 мин) и именно сюда чаще всего падают заказы |
| **2**   | **CRM API**            | Центральный узел подтверждения заказов и синхронизации статусов                   |
| **3**   | **RabbitMQ**           | Потерянные сообщения - одна из главных проблем (жалобы партнёров)                 |
| **4**   | **Shop API**           | Точка входа заказов, но проблем здесь меньше, чем в MES/CRM                       |
| **5**   | **Internet Shop / S3** | Проблемы здесь заметны сразу, но их проще диагностировать через мониторинг        |

## 3. Предлагаемое решение

| Компонент                            | Технология                                 | Обоснование                                               |
|--------------------------------------|--------------------------------------------|-----------------------------------------------------------|
| **Сбор логов**                       | Prometheus Pushgateway или экспортёры      | Сервисы сами отправляют логи в Prometheus                 |
| **Хранение логов**                   | Prometheus TSDB                            | Встроенное временное хранилище метрик                     |
| **Кэширование и временное хранение** | Redis (Streams / List)                     | Буферизация логов перед отправкой, хранение горячих логов |
| **Визуализация**                     | Grafana                                    | Единый интерфейс для всех логов и метрик                  |
| **Алертинг**                         | Prometheus Alertmanager + Grafana Alerting | Обнаружение аномалий и отправка уведомлений               |

### Политика безопасности

#### Принципы работы с чувствительными данными

- Запрещено логировать: email, телефон, адрес, паспорт, номер карты, пароль, токены.
- Допустимо с маскированием: user_id (хешируется), IP (маскируется последний октет).
- Разрешено без ограничений: order_id, trace_id, service, event, duration_ms, price, polygons_count.

#### Маскирование данных

- Фильтрация выполняется на уровне приложения до отправки в Redis.
- Log Exporter выполняет повторную фильтрацию для страховки.
- Хеширование user_id с солью для предотвращения деанонимизации.

#### Аудит доступа

- Логируются все запросы к Grafana (кто, когда, какой дашборд, какие фильтры).
- Логи аудита хранятся 1 год в отдельном файле / индексе.
- При подозрительной активности (более 100 запросов за минуту) - временная блокировка.

### Политика хранения логов

#### Где хранятся логи

| Тип данных                    | Хранилище       | Назначение                     |
|-------------------------------|-----------------|--------------------------------|
| Горячие логи (последние часы) | Redis Streams   | Буферизация, порядок сообщений |
| Метрики из логов              | Prometheus TSDB | Агрегация, алертинг, тренды    |
| Сырые логи (опционально)      | S3              | Долгосрочный архив             |

#### Сроки хранения

| Тип логов                            | Retention                          | Обоснование                         |
|--------------------------------------|------------------------------------|-------------------------------------|
| Redis Streams (горячие)              | 1 час (максимум 100 000 сообщений) | Для оперативной диагностики         |
| Prometheus метрики                   | 30 дней                            | Для анализа трендов и инцидентов    |
| Агрегированные метрики (downsampled) | 1 год                              | Для бизнес-отчётности               |
| S3 архив (если включён)              | 90 дней                            | Для расследования старых инцидентов |

#### Оценка размера

| Тип                    | Размер в месяц | Расчёт                                      |
|------------------------|----------------|---------------------------------------------|
| Redis Streams          | ~100 МБ        | 100 000 сообщений × 1 КБ                    |
| Prometheus TSDB        | ~5 ГБ          | 10 000 активных серий × 1.7 байта/серия/сек |
| S3 архив (опционально) | ~3 ГБ          | 3 млн логов × 1 КБ                          |

## 4. Превращение системы сбора логов в систему анализа логов

### Алертинг

Алертинг необходим. Его цель - оперативно реагировать на проблемы до того, как на них пожалуются клиенты.

**Какие события должны вызывать алерты:**

- **Частые ошибки** - если количество ERROR-логов превышает норму (например, более 10 за 5 минут), команда должна
  получить уведомление в Slack и автоматически созданный тикет в Jira.
- **Потеря сообщений** - если лог о публикации в RabbitMQ не сопровождается логом о потреблении в течение нескольких
  минут, это критическая ситуация: сообщение потеряно. Требуется вызов дежурного разработчика через PagerDuty.
- **Долгие операции** - если расчёт цены длится более 30 минут (при норме 2–3 минуты), это сигнал о проблеме с
  3D-моделью или производительностью MES. Нужно уведомить поддержку.

- **Зависшие заказы** - если заказ не перешёл в статус CLOSED через 24 часа после создания, он требует ручного разбора.

- **Проблемы с хранилищем** - если ошибки загрузки файлов в S3 превышают 5 в минуту, это может указывать на сбой или
  неправильные права доступа.

### Обнаружение аномалий

Поиск аномалий необходим. Система должна автоматически замечать нестандартное поведение, которое может быть признаком
атаки, сбоя или бага.

**Возможные типы аномалий:**

- **Внезапный рост ошибок** - вычисляется через статистическое отклонение от скользящего среднего. Если количество
  ошибок превышает среднее на три стандартных отклонения, это ненормально.

- **Исчезновение логов** - если от какого-то сервиса перестают поступать логи (например, MES молчит 5 минут), вероятно,
  сервис упал или завис.

- **Циклические аномалии** - один и тот же заказ меняет статус слишком часто (например, более 10 раз за час). Это
  указывает на баг в бизнес-логике.

## 5. Дополнительное задание: критерии выбора технологии для работы с логами

| Критерий                           | Prometheus + Redis + Grafana | ELK (Elasticsearch)     | Loki + Grafana      | OpenSearch              | Splunk        |
|------------------------------------|------------------------------|-------------------------|---------------------|-------------------------|---------------|
| **Лицензия**                       | Apache 2.0 / AGPL            | Elastic License         | AGPLv3              | Apache 2.0              | Проприетарная |
| **Хранение сырых логов**           | Redis (временное) + метрики  | Полнотекстовый индекс   | Объектное хранилище | Полнотекстовый индекс   | Проприетарное |
| **Поиск по order_id**              | Через метки (ограниченно)    | Полнотекстовый (быстро) | По меткам (быстро)  | Полнотекстовый (быстро) | Очень быстро  |
| **Интеграция с Grafana**           | Нативная                     | Через плагин            | Нативная            | Через плагин            | Отдельный UI  |
| **Требования к ресурсам**          | Низкие                       | Высокие (JVM)           | Средние             | Высокие (JVM)           | Очень высокие |
| **Горизонтальное масштабирование** | Redis Cluster + Thanos       | Да                      | Да                  | Да                      | Да            |
| **Полнотекстовый поиск**           | Нет                          | Да                      | Нет (только метки)  | Да                      | Да            |

### Обоснование выбора: Prometheus + Redis + Grafana

**Плюсы:**

- Минимальная стоимость (Redis + Prometheus легковесны)
- Единый стек с существующим мониторингом
- Простота развёртывания и поддержки
- Redis Streams обеспечивает гарантию порядка сообщений
- Нет лицензионных ограничений

**Минусы:**

- Нет полнотекстового поиска по логам
- Хранение сырых логов ограничено по времени (часы)
- Кардинальность меток ограничивает количество уникальных order_id
- Не подходит для больших объёмов (>500 ГБ/мес)
