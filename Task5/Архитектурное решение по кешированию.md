# Архитектурное решение по кешированию

## 1. Какие элементы системы кешируем

| Что кешируем                                                         | Почему                               |
|----------------------------------------------------------------------|--------------------------------------|
| Список заказов для дашборда (с фильтрацией по статусам и пагинацией) | Самый частый и тяжёлый запрос        |
| Агрегированные статистики (количество заказов в каждом статусе)      | Используется для фильтров и виджетов |
| Данные конкретного заказа (при просмотре деталей)                    | Частые чтения после загрузки списка  |

## 2. Мотивация

### Проблемы, которые решает кеширование

Операторы MES жалуются на низкую скорость работы страницы со списком заказов. Дашборд с фильтрами и пагинацией
загружается слишком долго, несмотря на уже проведённые оптимизации. При этом производственные мощности не загружены, а
клиенты недовольны скоростью выполнения заказов (косвенно страдают из-за того, что операторы медленно берут заказы в
работу).

**Что даст кеширование:**

- Снижение времени отклика дашборда с десятков секунд до миллисекунд.
- Уменьшение нагрузки на базу данных MES.
- Операторы смогут быстрее видеть новые заказы и брать их в работу - сокращение времени выполнения заказа для клиентов.
- Возможность масштабирования без деградации производительности.

## 3. Предлагаемое решение

### Тип кеширования: серверное

Выбираем **серверное кеширование**, а не клиентское.

**Почему не клиентское:**

- Браузер оператора не должен хранить данные между сессиями.
- Данные общие для всех операторов - кеш на стороне сервера позволяет всем видеть актуальную картину.
- Клиентское кеширование не снизит нагрузку на базу данных.

**Почему серверное:**

- Управляется централизованно.
- Единый источник правды для всех операторов.
- Легко инвалидировать при изменениях.

### Паттерн: Cache-Aside

Выбираем паттерн **Cache-Aside** (Lazy Loading).

**Как работает:**

1. При запросе данных приложение сначала проверяет кеш.
2. Если данные в кеше есть (hit) - возвращает их.
3. Если данных нет (miss) - загружает из базы данных, сохраняет в кеш, возвращает.

**Почему этот паттерн:**

- Самый простой в реализации.
- Подходит для сценариев с преобладанием чтения (дашборд читается гораздо чаще, чем меняется).
- Не требует сложной логики синхронизации.
- Нет риска переполнения кеша ненужными данными (загружается только то, что реально запросили).

**Почему не подходят другие паттерны:**

| Паттерн           | Почему не подходит                                                                                                                                                                   |
|-------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Write-Through** | При каждом изменении статуса пришлось бы писать и в БД, и в кеш. Это замедлит запись, а чтение дашборда всё равно не получит выгоды (кеш нужно перестраивать агрегированные данные). |
| **Refresh-Ahead** | Сложно предсказать, какие страницы дашборда понадобятся операторам в ближайшее время. Избыточное упреждающее заполнение кеша создаст лишнюю нагрузку.                                |

## 4. Стратегия инвалидации кеша

### Выбранная стратегия: программная (инвалидация по событию)

При каждом изменении данных (смена статуса заказа, создание нового заказа, назначение оператора) приложение
самостоятельно удаляет из кеша ключи, которые стали неактуальными. Дополнительно используется короткий TTL (30 секунд)
как страховочный механизм.

### Почему выбрана эта стратегия

Программная инвалидация позволяет гарантировать актуальность данных для критических операций (список доступных заказов
не должен показывать уже взятые). Короткий TTL служит fallback-механизмом на случай ошибок в логике инвалидации.

### Сравнение стратегий

| Критерий               | Программная (по событию)            | Временная (TTL)         | По ключу (версионирование) |
|------------------------|-------------------------------------|-------------------------|----------------------------|
| Актуальность данных    | Высокая (мгновенно после изменения) | Низкая (зависит от TTL) | Высокая                    |
| Сложность реализации   | Средняя                             | Низкая                  | Высокая                    |
| Нагрузка на Redis      | Высокая (частые удаления)           | Низкая                  | Средняя                    |
| Риск устаревших данных | Минимальный                         | Есть всегда             | Минимальный                |

**Программная лучше, потому что:**

- Обеспечивает актуальность списка заказов для операторов (заказ исчезает сразу после того, как его взяли).
- Позволяет инвалидировать только релевантные ключи (например, только по конкретному статусу), а не весь кеш.
- TTL служит страховкой, а не основным механизмом.

**Временная стратегия не подходит, потому что:**

- Оператор может видеть уже взятый заказ до 30 секунд, что приведёт к конфликтам (два оператора возьмут один заказ).
- Невозможно подобрать TTL, который одновременно обеспечит актуальность и хороший hit rate.

**Версионирование не подходит, потому что:**

- Слишком сложно для агрегированных данных (список заказов зависит от множества записей).
- Потребует хранить версию для каждого статуса и страницы, что увеличит сложность и потребление памяти.

### Особенности выбранной стратегии

1. При изменении заказа инвалидируются все ключи списков, где этот заказ мог присутствовать (по старому и новому
   статусу, а также смежные страницы).
2. Ключи деталей заказа инвалидируются точечно.
3. Короткий TTL (30 секунд) защищает от ситуаций, когда программная инвалидация по ошибке не сработала.
4. При недоступности Redis инвалидация пропускается (кеш устареет по TTL).

## Сравнение стратегий инвалидации кеша

| Программная (по событию)                                      | Временная (TTL)                                         | Версионирование (по ключу)                          |
|---------------------------------------------------------------|---------------------------------------------------------|-----------------------------------------------------|
| **Лучше подходит, потому что:**                               | **Позволяет:**                                          | **Позволяет:**                                      |
| Обеспечивает мгновенную актуальность данных                   | Простейшую реализацию без доп. кода                     | Точечную инвалидацию без потери данных              |
| Оператор сразу видит, что заказ уже взят                      | Гарантированное освобождение памяти                     | Атомарное обновление без гонок                      |
| Низкая нагрузка на Redis (только удаление)                    | Отсутствие риска "сбоя инвалидации"                     | Использование в распределённых системах             |

| 2. Нужно знать, какие ключи зависят от изменяемой сущности    | 2. Удалять данные мгновенно после изменения             | 2. Работать без версии в каждом запросе             |

| Версионирование - избыточно сложно для списков заказов        | Версионирование - не решает проблему агрегации          | TTL - не гарантирует актуальность                   |

## 5. Дополнительное задание: альтернативные решения кеширования

### Два варианта решения

| Критерий      | Решение 1: Cache-Aside с программной инвалидацией                                                                                                                     | Решение 2: Write-Through с агрегацией в реальном времени                                                                                                                                             |
|---------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Описание**  | При чтении: проверка кеша - при miss загрузка из БД - сохранение в Redis. При записи: обновление БД - удаление устаревших ключей кеша.                                | При записи статуса: обновление БД и одновременное обновление агрегированных данных в кеше (счётчики по статусам, список последних заказов). При чтении: данные всегда готовы.                        |
| **Диаграмма** | Чтение: Клиент - API - Redis (miss) - БД - Redis - Клиент. Запись: Клиент - API - БД - Redis (удаление ключей) - Клиент.                                              | Чтение: Клиент - API - Redis (данные уже есть) - Клиент. Запись: Клиент - API - БД - Redis (обновление агрегатов) - Клиент.                                                                          |
| **Плюсы**     | 1. Простота реализации. 2. В кеше только нужные данные. 3. Низкая нагрузка на Redis при записи (только удаление). 4. Легко масштабируется.                            | 1. Максимальная скорость чтения (всегда кеш hit). 2. Нет простоя при miss. 3. Счётчики и списки всегда актуальны.                                                                                    |
| **Минусы**    | 1. Первый запрос после записи медленный (cache miss). 2. Несколько операторов могут одновременно вызвать refresh. 3. При ошибке инвалидации данные устаревают до TTL. | 1. Сложная логика обновления агрегатов (списки, пагинация). 2. Высокая нагрузка на Redis при каждой записи. 3. Риск рассинхрона при частичном обновлении. 4. Трудно поддерживать порядок сортировки. |

### Заключение

**Выбирается Решение 1 (Cache-Aside с программной инвалидацией).**

**Почему:**

- Дашборд MES читается значительно чаще, чем изменяется. Write-Through создаст избыточную нагрузку на Redis при каждом
  изменении статуса (десятки раз в минуту), обновляя агрегаты, которые могут никогда не понадобиться.
- Программная инвалидация проще в реализации и отладке. Короткий TTL (30 сек) страхует от ошибок.
- Write-Through потребует пересчёта пагинированных списков при каждом изменении - это либо дорого (пересчёт всех
  страниц), либо сложно (инкрементальное обновление).
- Cache-Aside позволяет легко добавлять новые фильтры и сортировки - достаточно изменить запрос к БД, логика кеширования
  не меняется.
- Риск одновременного refresh при cache miss решается блокировкой (singleflight) в API.
